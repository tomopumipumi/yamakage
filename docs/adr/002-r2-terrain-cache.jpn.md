# ADR 002: 標高タイルデータの Cloudflare R2 キャッシュ採用

## 背景と課題
BFFにおいて日没時間を計算するためには、AWS Open Data 上でパブリック公開されている標高タイル画像（`s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png`）を取得・解析する必要があります。

1回の計算につき、現在地周辺の複数のタイル画像を取得する必要がありますが、毎回AWSのS3へ直接リクエストを送ると以下の課題が発生します。
1. **レイテンシの増加**: 外部サービス（AWS）へのHTTPリクエストがボトルネックとなり、Garminデバイスへのレスポンスが遅延します。
2. **帯域幅の無駄**: 地形データは事実上「不変」であるにも関わらず、同じ山域に複数のユーザーが訪れた際、あるいは同じユーザーが定期更新する際に、毎回同じ画像をダウンロードすることになります。
3. **外部依存の可用性リスク**: 稀にAWS側のS3がダウンしたり、レート制限に引っかかった場合、アプリ全体が機能不全に陥ります。

## 決定事項
AWSからの標高タイル取得の手前に、**Cloudflare R2 を利用したキャッシュ層**を導入します。

* タイル画像が必要な場合、まず R2（`yamakage-terrain-tiles` バケット）へ取得リクエストを行います。
* R2にデータが存在する場合はそれを即座に利用します。
* 存在しない場合はAWSから取得し、レスポンスをブロックしないように **Cloudflare Workers の非同期処理（`c.executionCtx.waitUntil`）を用いて裏側でR2へ保存**します。

## 結果と影響

### メリット
* **パフォーマンスの向上**: R2キャッシュヒット時、Cloudflareの同一ネットワーク内でのデータ取得となるためレイテンシが大幅に削減されます。
* **ユーザー体験の保護**: `waitUntil` を用いた非同期保存により、キャッシュミス時でも「R2への保存完了」を待たずに計算処理へ進めます。
* **コスト効率**: R2は下り転送料金が無料であるため、アクセスが増加してもインフラコストを低く抑えることができます。

### デメリット・トレードオフ
* **コードの複雑化**: `TileElevationRepository.ts` 内で R2 と AWS の両方にフォールバックするロジックや、`waitUntil` に渡す非同期関数のハンドリングを記述する必要が生じました。
* **ストレージ容量の増加**: 新しい場所で実行されるたびにR2の保存データ（容量）は蓄積していきます（地形データの不変性を考慮し、TTLは設定せず無期限キャッシュとする運用を許容しています）。
