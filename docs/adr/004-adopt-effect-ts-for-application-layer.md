# ADR 004: アプリケーション層の基盤として Effect (effect-ts) を採用


## コンテキスト

YAMAKAGE API のバックエンド（Cloudflare Workers）では、以下のように複数の非同期処理やリソース管理が複雑に絡み合う要件がありました。

### 1. **複雑な非同期 I/O のオーケストレーション**:
- Cloudflare R2（キャッシュ）へのアクセス
- R2 にない場合の AWS Open Data（S3）からの PNG タイル画像のフェッチと、バックグラウンド（`waitUntil`）での非同期キャッシュ保存
- 複数タイルの並行処理


### 2. **確実なリソース解放の必要性**:
- コア計算エンジンとして WebAssembly (Wasm) を採用したため、TypeScript 側で生成した Wasm インスタンスを、処理の完了後（またはエラー発生時）に必ず解放（`engine.free()`）し、メモリリークを防ぐ必要がありました。


### 3. **エラーハンドリングの不確実性**:
- 通常の `Promise` と `try/catch` では、関数がどのようなエラーを投げるかが TypeScript の型レベルで保証されず（常に `unknown`）、エラーのキャッチ漏れによる API サーバーのクラッシュ（500 エラーの予期せぬ発生）が懸念されました。


### 4. **Cloudflare 環境依存の分離 (DI)**:
- 環境変数（Bindings）やロガー、インフラリポジトリなどをビジネスロジック（ユースケース）に直接結合させず、テストや差し替えが容易な設計（依存注入: DI）が求められました。



## 意思決定

これらの課題を包括的かつ型安全に解決するため、TypeScript の強力な関数型エフェクトシステムである **[Effect](https://effect.website/) (effect-ts)** をアプリケーション層およびインフラ層の基盤として採用します。

### 具体的な設計と活用方針

#### 1. 宣言的で型安全なエラーハンドリング

すべての処理を `Effect<Success, Error, Requirements>` 型で表現します。独自のエラークラス（`ElevationFetchError` や `WasmError`）に `_tag` を持たせることで、どこでどんなエラーが発生し得るかをコンパイラが推論・検査できるようになり、`catchAll` 等による網羅的なエラーハンドリングを強制します。

#### 2. `Effect.acquireUseRelease` による確実な Wasm リソース管理

Wasm エンジンのインスタンス生成と解放を `Effect.acquireUseRelease` パターンでラップします。これにより、途中の処理（PNGのデコードやネットワーク通信など）で予期せぬ例外が発生しても、必ず `engine.free()` が実行され、エッジ環境におけるメモリリークを構造的に防ぎます。

```typescript
// 実際の実装例
Effect.acquireUseRelease(
  Effect.sync(() => new ShadowEngine()), // 獲得 (Acquire)
  (engine) => Effect.gen(function* (_) { /* Wasmを使った処理 (Use) */ }),
  (engine) => Effect.sync(() => engine.free()) // 解放 (Release)
)

```

#### 3. Context を用いた依存注入

クラスベースの巨大な DI コンテナフレームワーク（InversifyJSなど）は使用せず、Effect の `Context.GenericTag` と `Effect.provideService` を用いて、`Logger` や `ElevationRepository` などを型安全に注入します。これにより、ユースケース（`CalculateShadowUseCase`）から Cloudflare Workers 固有の実装を完全に切り離します。

#### 4. `Effect.gen` による可読性の確保

関数型プログラミング特有の深いメソッドチェーン（`pipe`）を避けるため、ジェネレータ構文（`Effect.gen` と `yield* _()`）を積極的に使用し、従来の `async / await` に近い直感的な可読性を維持します。

## 結果と影響

### メリット

#### **予期せぬパニックの防止**: エラーが型として可視化されたことで、外部 API の障害やデコードエラーなどを安全にハンドリングし、呼び出し元のルーター層で適切な HTTP ステータス（502や500など）にマッピングできるようになりました。
- **メモリリークの根絶**: Wasm のような手動メモリ管理が必要なリソースを、Effect の機能を用いて安全に統合できました。
- **クリーンアーキテクチャの実現**: インターフェース（`Context`）に依存する設計が自然に強制されるため、テスト時のモック化（`provideService`）が極めて容易になりました。
- **並行処理の最適化**: `Effect.all(..., { concurrency: 'unbounded' })` などにより、複数タイル画像の取得・デコード並行処理を簡潔かつ安全に記述できています。

### デメリット・トレードオフ

#### **高い学習コスト**: 開発メンバーが Effect の概念（ジェネレータ構文、Context、エラーチャネル、`pipe` など）や関数型プログラミングの基礎を理解するまでの学習曲線が存在します。
- **バンドルサイズの増加**: Effect は多機能なライブラリであるため、ビルド後の Workers バンドルサイズが素の TypeScript で書くよりも増加します（ただし、Cloudflare Workers の上限 1MB には十分に収まる範囲であり、実用上の問題はありません）。

## 代替案との比較

| 選択肢 | 評価 | 却下 / 採用理由 |
| --- | --- | --- |
| **ネイティブ `Promise` + `try/catch**` | 却下 | 学習コストはゼロでバンドルサイズも最小だが、エラーの型安全性がない（常に `unknown`）。Wasm のメモリ解放漏れ（`finally` の書き忘れ）のリスクが排除できず、堅牢性に欠けるため却下。 |
| **クラスベースの DI (InversifyJS / tsyringe)** | 却下 | サーバーレス関数のようなステートレスで軽量な実行環境においてはボイラープレートが多すぎ、デコレータ（`reflect-metadata`）への依存がバンドルサイズやパフォーマンスに悪影響を与えるため却下。 |
| **`fp-ts` / `neverthrow` (Result型のみ)** | 却下 | エラーの型安全化はできるが、DI やリソース管理、並行処理の機能が弱い。Effect はこれらを包括的に解決できるモダンな次世代ライブラリであるため、採用を見送り。 |
