# ADR 001: BFF (Backend For Frontend) アーキテクチャの採用

## 背景と課題
YAMAKAGEのコア機能は「現在地から周囲20km圏内の地形データを解析し、太陽の軌道と照らし合わせて本当の日没・日の出時刻を計算する」ことです。
初期構想において、この計算をクライアントであるGarminデバイス側で実行するか、サーバー側で実行するかの判断が必要でした。

Garminデバイス（特にDataFieldアプリ）には以下の厳しい制約が存在します。
1. **メモリ制限**: 多くのデバイスでDataFieldアプリのメモリ上限は32KBに制限されています。
2. **CPU・バッテリー制約**: 大量の標高タイル画像（PNG）のダウンロード、ピクセルごとのRGB値から標高へのデコード、および数百のサンプリングポイントに対する三角関数を用いた軌道計算は、ウェアラブルデバイスのCPUを大きく消費し、バッテリーを急速に枯渇させます。

## 決定事項
複雑な地形データの取得・パース・日没計算ロジックをすべて **Cloudflare Workers 上に構築した BFF** に委譲する設計を採用します。

* **Garmin側の責務**: GPS座標（緯度・経度）の取得とBFFへの送信。BFFから受け取った最小限の計算結果（分とUNIXタイム）の画面描画のみ。
* **BFF側の責務**: 外部APIからの地形データ収集、PNGデコード、サンプリングポイントごとの標高算出、SunCalcを用いた太陽軌道との交差判定。Garminデバイス向け（32KB制限をクリアするための極小配列）およびWeb向けのペイロード最適化。

## 結果と影響

### メリット
* **ハードウェア制約の回避**: Garminデバイスの厳しいメモリ・CPU制限をクリアできました。
* **バッテリー消費の最小化**: 重い演算をクラウド側で行うため、長時間の使用でもデバイスのバッテリーに影響を与えにくいです。
* **ビジネスロジックの共通化**: 計算ロジック（`CalculateShadowUseCase`等）をWeb版（`yamakage-site`）でも完全に再利用することが可能になりました。

### デメリット・トレードオフ
* **オンライン環境の必須化**: 計算にBFFを介するため、アクティビティ中はスマートフォンがBluetooth接続されており、かつモバイル通信圏内である必要があります。圏外の場所では最新の計算結果が受け取れません。
